### Question 1
The automated maze explorer implemented in the explorer.py module is based on a classical wall-following strategy known as the right-hand rule. This is a deterministic pathfinding algorithm where the explorer continuously attempts to keep its right "hand" in contact with a wall as it navigates through the maze. In practical terms, at each step, the explorer first attempts to turn right and move forward. If moving right is not possible, it then checks whether it can proceed in the current direction (straight). Failing that, it turns left to attempt a new direction. As a last resort, if all directions are blocked, it performs a 180-degree turn (two left turns) and moves forward, effectively backtracking out of a dead end.

Despite the simplicity of this algorithm, the explorer includes intelligent features to avoid getting stuck in infinite loops. It maintains a short history of the last few positions it visited using a fixed-size deque (a double-ended queue) called move_history. If the same position is repeated multiple times in succession — indicating that the explorer is circling without progress — a backtracking mode is triggered. During backtracking, the explorer attempts to retrace its steps to a previously visited node where there were multiple unexplored choices. This is implemented through the find_backtrack_path() method, which scans the historical move list to identify such decision points. Once a viable path is found, the explorer repositions itself and resumes exploration from that point.

To evaluate its performance, the explorer logs key statistics at the end of each run. These include the total time taken to solve the maze, the number of moves made, the number of backtrack operations, and the average number of moves per second. This data helps provide insight into the efficiency and behavior of the algorithm under different maze configurations. While this method guarantees a path to the goal in simply-connected mazes, it is inherently inefficient in terms of path length. For example, in the static maze, the explorer needed 1279 moves to reach the goal — far from optimal. This inefficiency arises because the algorithm does not prioritize direct paths or global knowledge of the maze. It blindly follows walls, which can result in traversing large unnecessary loops, especially in mazes with long corridors and few junctions. Therefore, although reliable, the right-hand rule serves more as a baseline or fallback strategy than a high-performance solution — and lays the groundwork for further improvement in subsequent parts of the assignment.

### Question 4
To address the limitations of the original maze explorer, I designed and implemented an enhanced explorer that replaces the right-hand rule algorithm with a graph-based search strategy — specifically, Breadth-First Search (BFS). This decision was motivated by the need to significantly reduce the number of moves taken to solve the maze and to guarantee an optimal solution. While the right-hand rule is effective in ensuring maze traversal, it lacks any form of global reasoning and frequently results in excessively long paths, especially in large or sparsely connected mazes. This was confirmed by the initial solution requiring 1279 moves, with no backtracking, due solely to the algorithm’s inherent inefficiency.

In contrast, BFS is a well-known shortest-path algorithm that explores all reachable nodes in a level-order manner, guaranteeing the discovery of the path with the fewest steps in unweighted grid environments like mazes. The enhanced explorer uses BFS to explore from the start node and records parent pointers to reconstruct the shortest path upon reaching the exit. The implementation was carefully integrated into the existing codebase by replacing the logic inside the Explorer.solve() method while preserving visualization capabilities and time/move tracking.

The results of this implementation are conclusive: when applied to the static maze, the enhanced explorer consistently produced a path length of 128 moves — a dramatic reduction from the original 1279. This number held true across all test cases and machines. The reason this value does not go lower is due to the fixed start and end positions defined in the static maze: specifically, (11, 0) as the entrance and (13, 49) as the exit. These coordinates are hardcoded in the StaticMaze class, and the path between them is constrained by the manually defined maze pattern. Because BFS guarantees the shortest possible path, the consistent result of 128 proves that this is the actual optimal path length under the given configuration.

Further experimentation with random mazes revealed additional strengths of the new explorer, where some paths were solved in as few as 52 or 98 moves, depending on the structure of the generated maze. This confirms that the enhanced algorithm not only achieves optimality but is also highly adaptable to different maze topologies.

In conclusion, the enhanced explorer successfully overcomes the primary limitations of the right-hand rule: excessive path length and lack of adaptability. By introducing BFS, the system now guarantees optimal traversal in both static and random maze environments. The consistency of the 128-move result on the static maze is not a failure of the algorithm, but rather a confirmation that the maze itself — and its fixed entry and exit — inherently require that many steps.

In conclusion, the BFS-enhanced explorer not only outperforms the original in every metric but also guarantees optimal results.
